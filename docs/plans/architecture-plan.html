Architecture plan · scout-agent · a greenfield re-core: a ~400-line kernel (event bus, plugin host, agent loop), everything else — including config, providers, tools, skills, and sessions — as internal plugins over one shared API; a single append-only SQLite event log as the source of truth, with message history as a projection. opencode2's constitution at pi's size.

1. Motivation

Scout v1 works and is small (~1,240 lines). But its center of gravity is wrong: agent.py and cli.py are the hub, and everything else is a spoke bolted on. Built-in tools are hardwired in cli.py; providers are hardwired in llm/; config validation hardcodes the provider list (scout/config.py:63); REPL commands are an if/elif chain (scout/cli.py:141-156); persistence is a direct call inside the agent loop; plugins get a guest API with a closed, four-event vocabulary (scout/plugins.py:17) while the interesting machinery — display, session writes, config — bypasses it entirely.

The result is that every feature lands in the core. There is no way to add a provider, a command, or a store without editing kernel files, and no way to remove one. Scout v1 is minimal by line count but not by structure.

opencode2 solved exactly this with one architectural move:

an architectural change we made in opencode2 is nearly everything is an internal plugin / there's 68 of them that cover our built in agents, integrations, config loading, etc — thdxr
OpenCode is the first time i could justify event sourcing in a real system / everything that happens is an event which gets projected into the sqlite db — thdxr

Scout v2 takes both ideas and neither of opencode2's costs: no 68 plugins, no TUI stack, no server/client split — eight internal plugins, one file each, in a package you can still read in an afternoon. The point is not to rebuild opencode; it is to give scout opencode's shape — tiny kernel, uniform extension surface, events as truth — at pi's size, and to make it fully mine: readable, maintainable, and deletable feature by feature.

Goals:

  • A kernel small enough to hold in your head (~400 lines): event bus, plugin host, agent loop, REPL shell. Nothing else.
  • One extension API for everything — scout's own features use the same API user plugins do.
  • A single append-only event log as the source of truth; message history, resume, and forking are queries/projections over it.
  • Every feature deletable: removing an internal plugin must degrade gracefully, never break the loop.
  • Still stdlib-only, still readable end-to-end, still ~1,400 lines total.

2. Research: opencode2, pi, Copilot CLI

opencode2

The two moves quoted above, in scout's terms:

opencode2 mechanismWhat it buys
Nearly everything is an internal plugin (68 of them: built-in agents, integrations, config loading, …) sharing one API with external plugins The core stops growing; features are symmetric (same registration path); users can override built-ins the same way they add features; the architecture is legible — to understand "how does X work," read X's plugin
Event sourcing: everything that happens is an event, projected into SQLite One durable record (no transcript/analytics drift); global sequence numbers; reverts and forks are events, not copy jobs; search/indexes are derived and rebuildable

pi

pi (badlogic) is the proof that a coding agent needs almost no core: a few-hundred-line agent loop, a handful of tools, and a deliberate refusal to grow machinery. Its lesson for scout is sizing, not structure: the value of a small core is that you can read it, trust it, and replace it. Scout v2 keeps pi's line-count discipline while adopting opencode2's organization.

Copilot CLI

Copilot's on-disk session layout (~/.copilot/session-state/<uuid>/ with events.jsonl, per GitHub's chronicle docs and reverse-engineering writeups) validated event-oriented session records. Scout v2 keeps the event orientation but centralizes: one SQLite store instead of per-session directories, because a global sequence number and atomic projections beat greppability for an agent's write rate (see §6).

3. Design principles

  • The kernel knows nothing. It may not import sqlite3, tomllib, or any builtin plugin. Kernel = bus + host + loop + shell + tool registry + HTTP. A test enforces this (§14).
  • One API, two kinds of user. Internal plugins and ~/.agents/plugins/*.py get the same PluginApi. Built-ins are just plugins that ship in the box and load first.
  • Events are the only memory. Anything worth remembering is an event in one append-only table. Views (message history, listings, dashboards) are projections; projections are rebuildable from events alone or they don't ship.
  • Failure is local. A broken subscriber, a failed plugin file, an unwritable store — warn and continue. The loop must survive every plugin, including scout's own.
  • Explicit beats clever. Three declared one-line seams between host and builtins (§5.5) instead of a service-indirection API. Greenfield, but no magic.
  • Stdlib only, Python 3.11+. sqlite3 and tomllib count as stdlib. Zero runtime dependencies, unchanged.

Three things to notice:

  • The loop is a pure emitter. agent.py holds no file handle and no database. Even the user message entering history is an event on the bus; the session plugin's subscription is what persists it. Because the bus is synchronous and the session plugin subscribes first, the projection is already updated when emit() returns — the loop can read session.messages immediately after emitting.
  • Persistence is a plugin. The kernel has no idea sessions exist beyond a read-only Session protocol (§5.4). Delete builtin/session.py and scout still runs, memory-only.
  • Display is a plugin. What v1 hardwired as display_hooks() in cli.py is now a subscriber that can be replaced or silenced.

5. The kernel

5.1 scout/bus.py add (~30 lines)

class Bus:
    def on(self, type: str, fn) -> None      # subscribe to ANY dotted event name
    def emit(self, type: str, **data) -> None # call subscribers in subscription order
  • Open vocabulary. No HOOKS tuple, no validation. Any dotted, lowercase name (tool.start, deploy.finished, anything a plugin invents) is legal. Cross-plugin integration needs no core change.
  • Synchronous, ordered, safe. Subscribers run in subscription order on the calling thread; a raising subscriber is reported to stderr and skipped — never fatal.

5.2 scout/host.py add (~120 lines)

def boot(cwd: Path, cli: dict) -> Runtime:
    # 1. registries + bus
    # 2. run builtin manifest in order, then .agents/plugins/*.py (user first,
    #    then project — later registration wins by name, so users override builtins)
    # 3. resolve layered config; pick provider; build client
    # 4. open session (new or resumed); emit session.start
    # 5. build system prompt; assemble Agent; return Runtime
  • Owns the four registries: tools (name → Tool), commands ("/fork" → callable), providers (name → client factory), prompts (list of paragraphs).
  • Plugin loading is v1's proven loader, minus the closed hook list: sorted *.py files from ~/.agents/plugins/ then ./.agents/plugins/, each executed, expecting a scout(api) function; failures warn and skip.
  • Later registration replaces earlier by name — so a user plugin can swap out a built-in tool or command. The inversion pays off here: overriding scout is identical to extending scout.

5.3 scout/agent.py rewrite (~65 lines)

Same loop as v1 in spirit; the difference is how it communicates:

def run(self, user_text: str, on_text=None) -> str:
    self.bus.emit("message.user", message={"role": "user", "content": [...]})
    for turn in range(...):
        message = self.client.complete(self.system, self.session.messages, ...)
        self.bus.emit("message.assistant", message=message, turn=turn + 1)
        ...
        for call in calls:
            self.bus.emit("tool.start", name=call["name"], args=call["input"])
            output, is_error = self.registry.dispatch(...)
            self.bus.emit("tool.end", name=..., args=..., output=..., is_error=...)
        ...
  • No session.append() calls, no emit(hooks, ...) helper — the loop only knows the bus, the registry, the client, and the read-only session view.

5.4 scout/cli.py rewrite (~95 lines) and the Session protocol

class Session(Protocol):
    id: str
    messages: list[dict]   # projection view; always current after emit() returns
  • cli.py is argument parsing, host.boot(), and a REPL whose command dispatch is a dict lookup into the command registry. Every command — /help, /clear, /fork, /skills, /plugins — is registered by a plugin. The if/elif chain is gone.
  • The protocol is read-only: the agent never writes history directly (writes are bus events consumed by the session plugin, §6).

5.5 The three declared seams

The host needs three things only builtins can provide. Rather than a service-registry API (considered, rejected — indirection costs readability), host imports three one-line factories from builtin/:

SeamSignatureProvided by
session factoryopen_session(cwd, config, resume: bool) -> Sessionbuiltin/session.py
prompt builderbuild_prompt(registry, skills, cwd, paragraphs, config) -> strbuiltin/prompt.py
skills loaderload_skills(cwd) -> dict[str, Skill]builtin/skills.py

These are the only kernel→builtin imports. Everything else flows through PluginApi. An import-lint test pins this (§14).

6. Event store & projector

6.1 One database, two tables

~/.scout/store.db (SQLite, WAL mode, single connection, commit per event):

CREATE TABLE events (            # the truth: append-only, never UPDATEd or DELETEd
  seq     INTEGER PRIMARY KEY,  # global, monotonic
  session TEXT  NOT NULL,       # uuid4().hex
  ts      TEXT  NOT NULL,       # UTC ISO 8601, fixed-width
  type    TEXT  NOT NULL,       # dotted name, open vocabulary
  data    TEXT  NOT NULL        # JSON object
);

CREATE TABLE messages (          # the projection: pure function of events
  session TEXT  NOT NULL,
  n       INTEGER NOT NULL,     # position within the session
  seq     INTEGER NOT NULL,     # originating event
  message TEXT  NOT NULL,       # JSON, Anthropic-normalized
  PRIMARY KEY (session, n)
);

6.2 Event vocabulary

Canonical events — open set, readers skip unknown types:

EventdataEmitted by
session.startcwd, model, pid, repository, branchsession plugin (boot, /clear)
session.forkfrom, at_n, cwd, model, pidsession plugin (/fork)
message.usermessageagent loop
message.assistantmessage, turnagent loop
tool.startname, argsagent loop
tool.endname, args, output, is_erroragent loop
plugin.loadedname, sourcehost
config.loadedconfigconfig plugin

Invariant: every session's first event is either session.start or session.fork (the fork event doubles as the new session's start; it carries the same metadata fields plus from/at_n).

6.3 The projector (~40 lines)

The complete rule set — the only code that interprets events:

On eventProjection effect
message.user / message.assistantappend row to messages for that session
session.forkcopy parent's rows n <= at_n into the new session
anything elseevents table only
  • Incremental: the session plugin tracks the last projected seq; each new event applies one rule.
  • Rebuildable: rebuild() drops messages and replays events. A test asserts incremental == rebuild, byte for byte (§14). Forking is a projector rule, not a copy job — which is what makes the projection a pure function.

6.4 Sessions, resume, fork

  • Session id: uuid4().hex; exists as a column value, not a directory.
  • Resume (scout -c): newest session.start/session.fork whose data.cwd equals the resolved working directory; per-directory scope, unchanged from v1/rev-2 decisions.
  • Fork (/fork [n]): emit one session.fork event (from = parent id, at_n = prefix length, default all); the projection inherits the prefix. The parent is untouched — no files copied, ever.
  • Legacy: v1 <cwd>/.scout/sessions/*.jsonl and the rev-2 ~/.scout/sessions/<uuid>/ layout are ignored. No migration.

6.5 Why this beats the rev-2 dual-file design

  • No drift, by construction. Rev-2 kept messages.jsonl (truth for content) and events.jsonl (truth for timing) — two files that can disagree. v2 has one truth and one derived view.
  • Global sequence numbers for free. Ordering across sessions, incremental projection checkpoints, and future compaction ("events before seq N are summarized in …") all hang off seq.
  • Queryable history. Resume-by-cwd, fork lineage, "sessions from last week" are one-liners in SQL instead of directory scans.
  • Still inspectable: sqlite3 ~/.scout/store.db 'select * from events' on any machine with Python. JSONL's greppability is the real loss; accepted.

7. Plugin API v2

Breaking change; greenfield. Superset of v1 in spirit (“a plugin is a Python file exposing scout(api)”), reworked around the open bus:

def scout(api):
    api.tool(Tool(...))                    # register/replace a tool by name
    api.on("tool.end", fn)                 # subscribe to ANY event (open vocabulary)
    api.prompt("Deploy only on request.")  # append a system-prompt paragraph
    api.command("/deploy", fn)             # REPL command; fn(agent, rest_of_line)
    api.provider("groq", factory)          # factory(config) -> client; selectable via config
    api.config({"deploy_timeout": 10})     # declare config keys + defaults
MethodNotes
tool(tool)replaces register_tool; later wins by name — user plugins can replace built-ins
on(event, fn)no closed hook list; subscriber exceptions are caught and reported by the bus
prompt(text)unchanged from v1
command(name, fn)new; how /fork, /skills, even /help exist
provider(name, factory)new; anthropic/openai register this way too, so adding groq/local is a plugin
config(defaults)new; declares keys merged into layering: plugin defaults < user toml < project toml < SCOUT_* env < CLI flags

Worked example — a user plugin adding a provider, a command, and a tool:

# ~/.agents/plugins/deploy.py
from scout.tools import Tool

def deploy_now(agent, rest): ...

def scout(api):
    api.provider("groq", lambda cfg: openai_compat(base_url="https://api.groq.com/openai/v1", cfg))
    api.command("/deploy", deploy_now)
    api.tool(Tool(name="deploy", description="Deploy the current branch.",
                  parameters={...}, run=deploy))
    api.on("tool.end", lambda name, **_: print(f"done: {name}"))
    api.prompt("Deploy only when explicitly asked.")

v1's examples/plugins/ are rewritten to this API in the rollout (§12, phase 5).

8. Internal plugins

scout/builtin/ — one file per feature, loaded by an ordered manifest in __init__.py. Order matters twice: session subscribes before display (so projections are current when other subscribers observe events), and config loads first (its defaults seed layering).

Each is deletable: remove display and scout goes quiet; remove session and it runs memory-only; remove skills and the skill tool and prompt section vanish together. That is the test of the inversion — and the difference from v1, where each of these was load-bearing in the core.

8.1 Prompt caching

OpenAI-compatible endpoints prefix-cache automatically, server-side — no markup, no code. Anthropic caching is opt-in, so builtin/providers/anthropic.py inserts cache_control breakpoints into its wire format (~25 lines: one on the system-prompt tail, one on the last block of the prior turn). That is the entire caching story: a wire-format concern inside one provider plugin. The kernel loop, the normalized message format, and the event store stay cache-agnostic, and hits are already guaranteed by the architecture's byte-stable prefix — system prompt built once, append-only message projection, deterministic tool ordering from the ordered manifest. No config keys, no usage tracking.

13. Release & CI pipeline

Two small GitHub Actions workflows, both standard-shaped. Neither adds runtime dependencies — build and pytest are dev-time only, installed by the runner, never listed in pyproject.toml beyond the existing [dev] extra.

.github/workflows/ci.yml — tests on every push and PR

name: ci
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ["3.11", "3.12", "3.13"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
      - run: pip install -e .[dev]
      - run: pytest -q

This is the enforcement story for §14: kernel purity, projector determinism, and append-only store invariants run on every push, not just locally.

.github/workflows/release.yml — tag push publishes to PyPI

name: release
on:
  push:
    tags: ["v*"]

permissions:
  id-token: write   # OIDC: no stored PyPI secrets

jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
      - run: pip install build && python -m build   # sdist + wheel
      - uses: pypa/gh-action-pypi-publish@release/v1
  • Trigger: pushing a tag matching v* builds and publishes. No manual dispatch, no UI step — git tag v2.0.0 && git push --tags is the whole release procedure.
  • Auth: PyPI trusted publishing (OIDC). The workflow exchanges a GitHub-attested identity token for a short-lived PyPI token; no API token is stored as a repo secret.
  • One-time manual prerequisite (cannot be done from the repo): on pypi.org → Publishing → add a trusted publisher for project scout-agent, owner dairycow, workflow release.yml, environment (none). Until the project exists on PyPI, the first release uses the pending-publisher flow (reserve the name, then register the publisher).
  • Version discipline: the tag must equal the version field in pyproject.toml (first release: v2.0.0). A mismatched tag is the only way to publish a wrong version; the plan adds a tiny consistency check (assert tag == version) as the workflow's first step rather than reaching for external action tooling.
  • Artifacts: one sdist + one wheel from python -m build; the package is pure-Python stdlib-only, so no platform matrix is needed for publishing.

All store tests monkeypatch the store root to a pytest tmp_path; nothing ever touches the real ~/.scout. Fake clients as in v1 — the suite stays offline.

15. Decisions & non-goals

Decision log (user-confirmed)

  • Greenfield re-core, same repo. No compatibility with v1 internals or the v1 external plugin API; built on one branch, v1 deleted at phase 5. The product surface (REPL, -p, -c) is preserved.
  • Full inversion. Kernel = bus + host + loop + shell + tool registry + HTTP (~440 lines). Config, providers, tools, skills, sessions, prompt, display, commands are all internal plugins on the same PluginApi as user plugins.
  • Events are the source of truth. Single append-only SQLite events table at ~/.scout/store.db; messages is a projection with a deterministic projector; fork is a projector rule; resume is a query. Supersedes rev-2's dual-file design.
  • Stdlib-only stays. dependencies = [] unchanged; sqlite3/tomllib qualify.
  • .agents/ convention stays. Plugins and skills keep loading from the shared cross-tool directories, project overriding user.
  • v1 sessions ignored. No migration, no fallback read (carried over from rev 2).
  • Loop is a pure emitter. The agent never touches the store or the filesystem; even message persistence is a bus subscription owned by the session plugin.
  • Three declared seams. Host imports open_session, build_prompt, load_skills from builtins — the only kernel→builtin coupling; pinned by an import-lint test.
  • CI on every push/PR. ci.yml runs pytest -q on a 3.11–3.13 matrix; the invariant tests of §14 are release gates, not local courtesies.
  • Releases are tag pushes. v* tag → build sdist+wheel → publish to PyPI; tag must equal pyproject.toml's version; first release is v2.0.0.
  • OIDC trusted publishing, no stored secrets. id-token: write + pypa/gh-action-pypi-publish; no PYPI_API_TOKEN in repo secrets; one-time publisher registration on pypi.org is the only manual step.
  • Build tooling is dev-time only. build/pytest are installed by runners (or the [dev] extra); dependencies = [] is untouched.

Non-goals (deliberately out of scope)

  • opencode2's scale: no 68 plugins, no server/client split, no multi-session concurrency, no TUI framework (plain print/input stays)
  • Event-sourcing machinery beyond the 40-line projector: sequence-number APIs, context epochs, compaction checkpoints, staged reverts — though the event schema leaves room (seq makes a future context.compacted projection rule cheap)
  • SQLite FTS/search UI over sessions; cloud sync; permission prompts; MCP; LSP
  • Config UI beyond toml/env/flags; no sessions_dir override (hardcoded, per rev-2 decision)

Every non-goal can layer on later without format changes: the store is append-only and projection is rebuildable, the bus vocabulary is open, and built-ins are plugins — which is the whole point of the redesign.

Goal

Cut the two real costs in scout's wall clock and add the observability to prove it:

  1. Retry with backoff — one transient 429/5xx no longer kills a run. scout/http.py currently has zero retry: any 429/500/529 becomes ScoutError, cli.py prints it, and the whole turn — prompt already paid for — is discarded. Survivable when you retype a prompt; fatal mid-run.
  2. Usage events + meter — per-turn token counts incl. Anthropic cache hit/creation; tokens only, no prices. Display surface: a statusline slot (sibling statusline branch) plus the /usage command — see cross-branch.
  3. Parallel tool execution — multi-tool turns go from sum(durations) to max(durations).

Non-goals

  • Cost estimates / price tables — token counts only.
  • Partial or per-tool parallelism policy — all tools in parallel behind one kill-switch.
  • Building the statusline here — it already exists on the statusline branch (d6ba8c6); this PR only feeds it a usage event.

Design notes per feature

Retry (C2)

  • Why it's an issue even if you haven't seen it. Today http.py maps every HTTPError/URLError straight to ScoutError, and cli.py prints-and-continues. In the REPL that just costs a retyped prompt. In a long tool loop it discards a turn whose full prompt (system + all history + tool results) was already paid for, and C4's burst of tool-result re-entries makes transient 429/529 more likely, not less. Anthropic returns 529 (overloaded) routinely at peak; one 30s backoff turns a dead run into a pause.
  • Retry only pre-stream failures; once the first SSE event yields, a later failure raises (no duplicated text).
  • Retryable: 429/500/502/503/504/529 + URLError; everything else raises on attempt 1.
  • Backoff 0.5·2ⁿ + jitter, cap 8s; Retry-After honored, cap 30s. retries=2 default + CLI/env.

Usage (C3)

  • Client protocol: complete(..., on_usage=None); providers call on_usage(dict) once at stream end.
  • Normalized fields: input_tokens, output_tokens, cache_read_input_tokens, cache_creation_input_tokens.
  • Agent buffers the callback; bus.emit("usage", ...) right after message.assistant.
  • Display: the statusline slot — statusline.py (sibling branch, d6ba8c6) already renders a dim key=value line per user turn and subscribes near message.assistant; since usage is emitted immediately after it, the slot store picks up a tok=… segment with no new seams. Until that branch merges, /usage prints session totals on its own.
  • /usage command prints session totals.

Parallel tools (C4)

  • When len(calls)>1 and parallel_tools: emit all tool.start, dispatch on ThreadPoolExecutor(min(n,8)), emit tool.end as futures complete, reassemble by index.
  • All bus emits on the main thread — sqlite is check_same_thread=True.
  • Kill-switch parallel_tools=true + --no-parallel-tools + SCOUT_PARALLEL_TOOLS (new bool coercion in host.py).
  • Single-call and kill-switch paths keep the exact serial event sequence (pinned by test_loop_events).
  • Depends on C2 landing first: the burst of parallel re-entries raises transient-429 odds, and without retry that kills the run (see topology note).

Cross-branch: usage × statusline

Where usage displays. Not in this PR's display code. The sibling statusline worktree (branch statusline, commit d6ba8c6) ships scout/builtin/statusline.py: a named-slot store rendered as one dim line per completed user turn, subscribing to session.start / message.assistant / display.stderr. This PR's contract with it is one event: usage, emitted right after message.assistant — statusline (or a thin follow-up there) adds a tok=… slot. No kernel seams, no config, nothing else.

Overlap to manage. Both branches edit builtin/__init__.py (MANIFEST row) and README.md (plugin table/counts). Merge statusline first; this PR rebases (one MANIFEST line, one README row), and C5 refreshes the README against the post-merge tree. This PR does not touch statusline.py.
